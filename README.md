# AutoGuard

**AutoGuard** — навчальний вебзастосунок для лабораторної роботи №6 «Розробка безпечної системи управління обліковими записами». Поєднує захищені облікові записи з особистим гаражем, історією технічного обслуговування й обліком витрат. Інтерфейс українською, адаптивний дизайн у темно-синій палітрі. Потрібен Python **3.11+**.

Перевірки: **98 pytest-тестів**, окремий наскрізний HTTP-прогін — **23 перевірки**. Документація: [аудит семи завдань](LAB6_AUDIT_REPORT.md), [актуальна перевірка Google OIDC](GOOGLE_OIDC_CHECK.md), [чекліст відеозахисту](VIDEO_DEMO_CHECKLIST.md). У звітах розділено mocks, справжні HTTP-виклики та ручні сценарії, які ще потребують перевірки.

## Технологічний стек

| Частина | Технології |
|---|---|
| Backend і сервер | Python 3.11+, Flask, Waitress |
| Дані та міграції | SQLite, Flask-SQLAlchemy, Flask-Migrate / Alembic |
| Інтерфейс | HTML5, CSS3, JavaScript, локальний Bootstrap 5 |
| Облікові записи й форми | Flask-Login, Flask-WTF, Argon2id, Flask-Limiter |
| Другий фактор | PyOTP TOTP, QR-коди, Fernet / cryptography |
| Зовнішні сервіси | Authlib Google OpenID Connect, Cloudflare Turnstile, SMTP STARTTLS |
| Перевірки | pytest, pip check, pip-audit; сканування секретів перед публікацією |

## Відповідність лабораторній №6

| № | Завдання | Реалізація |
|---|---|---|
| 1 | Реєстрація та автентифікація | Політика складних паролів, Argon2id, вхід/вихід, профіль, захищені сесії |
| 2 | CAPTCHA | Turnstile на реєстрації та серверна Siteverify-перевірка |
| 3 | Активація через email | Одноразовий токен із терміном дії, статус у профілі, повторне надсилання |
| 4 | Brute Force та RBAC | Ліміти за IP/email, тимчасове блокування, USER/ADMIN, журнал і ручне блокування |
| 5 | 2FA | TOTP, QR-код, увімкнення/вимкнення, зашифрований секрет |
| 6 | Зовнішній вхід | Google OIDC Authorization Code + PKCE, state/nonce/ID Token |
| 7 | Відновлення пароля | Email-посилання, одноразовість, строк дії, новий пароль і відкликання сесій |

Після активації USER керує лише власними авто та записами. ADMIN бачить користувачів, їхні статуси й журнал, може блокувати/розблоковувати акаунти. Створення ADMIN доступне тільки через CLI. Реальні SMTP, OIDC і production CAPTCHA потребують власної конфігурації: credentials до репозиторію не входять.

## Запуск у Windows / VS Code

Встановіть Python 3.11+, Git та розширення Python для VS Code. У PowerShell клонуйте проєкт:

```powershell
git clone https://github.com/Nazarii-Tsiuniak/AutoGuard.git
cd AutoGuard
```

Відкрийте цю папку у VS Code. Якщо проєкт уже відкрито в `lab6/autoguard`, повторно клонувати або виконувати `cd` не потрібно. У терміналі **з кореня AutoGuard**:

```powershell
py -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
if (!(Test-Path .env)) { Copy-Item .env.example .env }
.\.venv\Scripts\python -m flask --app run db upgrade
.\.venv\Scripts\python run.py
```

Відкрийте **http://127.0.0.1:5050**. Активація PowerShell-середовища не потрібна. У VS Code: **Python: Select Interpreter → .venv\Scripts\python.exe**. `db upgrade` створює схему нової локальної БД або застосовує відсутні міграції. Сервер слухає лише loopback, debug вимкнений. `run.py` використовує Waitress без журналювання URL, які можуть містити одноразові токени. Для зупинки — Ctrl+C. Не перезаписуйте наявний `.env` та не видаляйте `instance/` при повторному запуску.

Після реєстрації увійдіть і відкрийте профіль. До активації доступні профіль та повторне надсилання листа. Листи в локальному режимі зберігаються лише в `instance/mail/*.eml`. Відкрийте найновіший `.eml` у редакторі, скопіюйте URL активації в браузер і підтвердьте активацію кнопкою. Альтернатива — команда нижче; вона навмисно показує локальні листи з одноразовими посиланнями, тому її вивід не слід публікувати:

```powershell
.\.venv\Scripts\python -m flask --app run list-mail
```

У локальному режимі використовуються офіційні тестові ключі Cloudflare. CAPTCHA все одно перевіряється сервером, для реєстрації потрібний Інтернет. Якщо Cloudflare недоступний, реєстрація відхиляється; прихованого обходу CAPTCHA немає. Bootstrap, CSS, JavaScript та SVG збережені локально.

## Можливості

У формах додавання й редагування автомобіля марки та моделі мають пошукові випадні підказки. Список моделей залежить від марки; для вже збереженого авто він підвантажується автоматично. Поле «Тип робіт» пропонує базові обслуговування та ремонти. В усіх трьох полях дозволено вводити власний текст. Початковий локальний каталог зберігається в `autoguard/static/form-options.json`, його можна розширювати без зміни БД. Відкрийте поле та почніть вводити назву; вигляд списку залежить від браузера.

Рік, пробіг і вартість вводяться вручну без стрілок та зміни значення колесом миші. Дата обслуговування — ручний ввід `ДД.ММ.РРРР`. Вартість приймає кому або крапку як десятковий роздільник. Кнопка **«Додати ще роботу»** додає окреме поле з підказками або довільним текстом; зайву роботу можна прибрати кнопкою ×. В одному записі — до 20 робіт, кожна до 120 символів, одна дата, пробіг і **загальна вартість всього запису**. Історія показує всі роботи, а статистика враховує загальну суму один раз. Старі записи з однією роботою зберігаються; міграція `790d0bcb1f02` розширює поле робіт до Text.

- Реєстрація, вхід, POST-вихід, редагування імені, ролі USER/ADMIN, статус активації.
- Argon2id із випадковою сіллю, політика пароля та індикатор складності.
- Turnstile на клієнті та сервері; перевірка hostname/action у production.
- Активація та скидання пароля: випадкові токени, SHA-256 у БД, 30 хвилин, атомарне одноразове використання, повторний лист не частіше разу на хвилину.
- Після зміни пароля або адміністративного блокування всі попередні сесії, включно з незавершеними 2FA, недійсні.
- Вихід також відкликає всі попередні сесії акаунта, щоб скопійований cookie не працював після logout. Абсолютні 30 хвилин рахуються від завершення входу й не подовжуються через повідомлення або оновлення cookie.
- 5 невдалих спроб входу/2FA за email за 15 хвилин блокують вхід на поточне вікно; IP-ліміт входу — 20 POST за 15 хвилин. Облік спроб за email діє незалежно від IP. Повторні спроби під час блокування подовжують вікно.
- TOTP через PyOTP, локальний QR-код, підтвердження ввімкнення, зашифрований Fernet-секрет, відхилення повторного коду, обмеження спроб. До другого фактора повної сесії немає. Вимкнення потребує нового TOTP і поточного пароля; для Google-only акаунтів — нового TOTP.
- Google OIDC Authorization Code + PKCE, state/nonce та валідація ID Token через Authlib. Google `sub` є ідентифікатором; збіг email не прив’язує акаунти. Пов’язування доступне в авторизованому активованому профілі через POST із CSRF. Вимоги 2FA та блокування застосовуються до Google-входу.
- CRUD автомобілів, історія ТО, додавання/редагування/видалення записів, витрати за місяцями та автомобілями. Вартість — Decimal/Numeric, не float у БД. Пробіг оновлюється вгору після ТО; видалення історичного запису не зменшує пробіг авто.
- Панель адміністратора: пошук, активація, невдалі спроби, блокування/розблокування, журнал. Секрети, хеші паролів і токени у шаблони адміністратора не передаються як поля для відображення. Адміністратора не можна блокувати через вебпанель.
- CSRF на всіх змінах стану, ORM-запити, Jinja-екранування, серверна перевірка власника, заголовки CSP, захист від вбудовування, cookies HttpOnly/SameSite, абсолютний строк сесії 30 хвилин.

## Перший адміністратор

```powershell
.\.venv\Scripts\python -m flask --app run create-admin
```

Введіть email, ім’я й надійний пароль у прихованому запиті термінала. CLI створює активованого адміністратора. Публічна реєстрація завжди дає USER; існуючий email CLI не підвищує до ADMIN. Пароль не передавайте аргументом командного рядка в реальному використанні.

## Google OAuth

1. У Google Cloud створіть проєкт, налаштуйте OAuth consent screen та додайте тестових користувачів, якщо застосунок у режимі Testing.
2. Створіть OAuth client типу **Web application**. Authorized redirect URI: `http://127.0.0.1:5050/auth/google/callback` (або HTTPS-домен production з тим самим шляхом).
3. Запишіть `GOOGLE_CLIENT_ID` та `GOOGLE_CLIENT_SECRET` у `.env`, перевірте `PUBLIC_BASE_URL`, перезапустіть сервер.
4. Для існуючого локального email спочатку увійдіть локальним паролем, відкрийте «Безпека» та натисніть «Пов’язати Google-акаунт». Без цього автоматичне прив’язування відхиляється.

Якщо ключів немає, локальний вхід працює, а інтерфейс пояснює відсутність налаштування. Деталі в [офіційній документації Authlib](https://docs.authlib.org/en/latest/oauth2/client/web/flask.html).

`.env` завантажується з кореня AutoGuard під час запуску; уже запущений Waitress не перечитує його після збереження файлу. Після зміни credentials потрібно зупинити попередній процес і запустити `python run.py` знову. При старті виводиться тільки `Google OIDC: configured / missing`. Команда `.\.venv\Scripts\python -m flask --app run oidc-status` також показує лише configured/missing, без значень. Вона перевіряє новий процес; якщо команда показує configured, а старий сайт — «не налаштовано», перезапустіть саме сервер, що слухає 5050. Системні змінні мають пріоритет над `.env` (`override=False`); не замінюйте глобально цю політику заради OAuth, щоб не зачепити SMTP або інші секрети.

## CAPTCHA

Створіть Turnstile widget у Cloudflare для вашого домену. У `.env` встановіть справжні `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `TURNSTILE_HOSTNAME` (hostname без протоколу). Для localhost залиште офіційні dummy-ключі з `.env.example`. Токен передається сервером на Siteverify з timeout; відмова, некоректна відповідь і мережевий збій відхиляють реєстрацію. Див. [тестові ключі](https://developers.cloudflare.com/turnstile/troubleshooting/testing/) і [серверну валідацію](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

## Email

### Швидке налаштування Gmail

1. Увімкніть двоетапну перевірку у своєму Google-акаунті.
2. Відкрийте [Паролі застосунків Google](https://myaccount.google.com/apppasswords) і створіть окремий пароль для AutoGuard. Звичайний пароль Gmail не використовуйте. Якщо опція недоступна, перевірте [обмеження Google](https://support.google.com/mail/answer/185833).
3. У терміналі VS Code з папки `lab6/autoguard` виконайте:

```powershell
.\.venv\Scripts\python configure_gmail.py
```

Введіть адресу відправника Gmail і 16-символьний пароль застосунку (пробіли між групами дозволено). Введення пароля приховане. Майстер зберігає дані тільки в ігнорований `.env`, зберігає інші параметри й перемикає `MAIL_MODE=smtp`. Дані в чат надсилати не потрібно. До завершення майстра залишається локальний файловий режим.

4. Зупиніть AutoGuard через Ctrl+C та знову запустіть `python run.py` із `.venv`. У профілі натисніть «Надіслати лист повторно»; між запитами має минути хвилина. Перевірте вхідні листи та «Спам». Старі `.eml` не надсилаються автоматично.

Gmail використовує `smtp.gmail.com:587` із STARTTLS; `MAIL_FROM` і `SMTP_USER` майстер встановлює рівними вашій адресі. Це відповідає [SMTP-параметрам Google](https://support.google.com/mail/answer/7104828). Налаштування відправника не пов’язане з кнопкою «Увійти через Google» — OAuth-вхід налаштовується окремо. Посилання `127.0.0.1:5050` слід відкривати на тому самому комп’ютері, де працює AutoGuard.

Для реальної пошти змініть `MAIL_MODE=smtp`, `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT=587`, `SMTP_USER`, `SMTP_PASSWORD`. Використовується обов’язковий STARTTLS із перевіркою сертифіката. За потреби використайте пароль застосунку від провайдера. Перевірте дозволеного відправника й доставку активації/скидання вручну. Порт 465 з implicit TLS цією конфігурацією не підтримується. SMTP-помилки не виводять вміст листа або credentials у лог; користувач може повторити запит через хвилину.

Профіль тепер відрізняє SMTP-прийняття, файловий режим, cooldown і помилку доставки. При помилці новий токен відкочується разом із транзакцією, попереднє робоче посилання не відкликається. Повідомлення відновлення пароля залишається однаковим для відомої та невідомої адреси.

## Production

Production потребує окремого налаштування: `APP_ENV=production`, HTTPS у `PUBLIC_BASE_URL`, справжні CAPTCHA-ключі й hostname, SMTP та спільне сховище Flask-Limiter. Для Redis встановіть `pip install redis` у це середовище та задайте `RATELIMIT_STORAGE_URI=redis://127.0.0.1:6379/0`. Redis не потрібний локально. Параметри production перевіряються при старті; dummy CAPTCHA, локальна файлова пошта та memory-сховище лімітів відхиляються.

Згенеруйте ключі окремо й перенесіть у захищений `.env` або менеджер секретів:

```powershell
.\.venv\Scripts\python -c "import secrets; print(secrets.token_hex(32))"
.\.venv\Scripts\python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Перше значення — `SECRET_KEY`, друге — `TOTP_ENCRYPTION_KEY`. Зберігайте резервну копію encryption key окремо від БД: його втрата робить наявні TOTP-секрети недоступними. Локальні випадкові ключі автоматично зберігаються в `instance/`; не видаляйте їх при звичайному перезапуску. Розміщуйте застосунок за HTTPS reverse proxy; не довіряйте довільному `X-Forwarded-For`. Для коректного IP-ліміту за проксі налаштуйте довіру лише до відомої кількості власних проксі. Масштабування, резервні копії, ротація ключів і політика зберігання аудиту потребують окремого операційного налаштування. Це навчальна реалізація, без зовнішнього аудиту безпеки.

## Міграції та перевірки

Для аудиту залежностей: встановіть `requirements-dev.txt`, потім виконайте `python -m pip_audit --progress-spinner off`. Після оновлення залежностей повторюйте цей скан; відсутність advisory у ньому не замінює аудит коду. `python local_http_audit.py` запускає власний тимчасовий сервер і БД, перевіряє справжні HTTP/CSRF та Cloudflare Siteverify з dummy-ключами, зберігає `local-http-audit.json`; ваші акаунти й реальну пошту не використовує.

```powershell
.\.venv\Scripts\python -m flask --app run db upgrade
.\.venv\Scripts\python -m flask --app run db check
.\.venv\Scripts\python -m pytest -q --tb=short -p no:cacheprovider
.\.venv\Scripts\python -m pip check
```

Після зміни моделей: `flask --app run db migrate -m "Опис зміни"`, перевірка створеного файлу, `db upgrade`. Початкова міграція вже збережена в `migrations/versions/`. Pytest використовує окрему SQLite in-memory БД, тимчасову файлову пошту та mocks мережевих сервісів; не змінює робочу БД. Окремий HTTP-прогін працює з тимчасовою файловою SQLite та справжнім тестовим Siteverify. Gmail STARTTLS/авторизацію перевірено без нових листів; нове отримання листів, реальний Google-вхід і production Turnstile під час аудиту не перевірялися. Деталі — у `VERIFICATION.md` і `LAB6_AUDIT_REPORT.md`.

Репозиторій: [Nazarii-Tsiuniak/AutoGuard](https://github.com/Nazarii-Tsiuniak/AutoGuard). Корінь Git має охоплювати тільки AutoGuard, без інших лабораторних. `.gitignore` виключає `.env` та його локальні варіанти, `instance/`, бази й SQLite sidecar-файли, пошту, ключі, сертифікати, логи, резервні копії, кеші та віртуальні середовища. `.env.example` містить лише порожні значення та публічні dummy-ключі Cloudflare.

Перед кожним комітом перевіряйте `git status --short`, `git diff --cached --stat`, staged-вміст та історію сканером секретів, наприклад Gitleaks із `--redact`. **Не публікуйте паролі Gmail, Google Client Secret, Flask/Fernet-ключі, листи з токенами або робочу БД.** Не передавайте credentials у чат, скриншоти, відео чи команди Git. Якщо credential був розкритий, його потрібно відкликати в сервісі та замінити локально: видалення з файлу не відкликає доступ.

Історичні звіти аудиту відображають стан на момент їх створення; актуальні перевірки Google описані окремо в `GOOGLE_OIDC_CHECK.md`. Наявність коду в GitHub не є публічним розгортанням сервера й не налаштовує SMTP/OAuth для того, хто клонує проєкт.
